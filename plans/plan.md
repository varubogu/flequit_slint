### 1.3 実装時の判断

- 期限キーワードは「名前付き（今日・今年度など）/ 日数 / 分数」を区別して持つ（`DueSpec`）。
  日数に丸めると `@今年度` が `@365日` として書き戻されるため
- 「入力中」の語は直前の編集位置で判定する。`LineEdit` はキャレット位置を公開しない
- `-` の直後が確定済みトークンのとき、字句解析はセグメントごとに行うため `-` が単独扱いになる。
  構文解析側で「テキストの末尾の `-` + 次が確定トークン」を NOT として扱う
- `*` を含む語が何も指さないときは、他の未解決の `@` と同じく無視して警告する（一覧を空にしない）
- サブタスクの `completed` フラグ（旧フィールド）が立っていれば、状態が追いついていなくても完了として扱う
- タスク自身が当たったときはサブタスクに一致の印を付けない（所属・自由語を継承するため、印が意味を持たなくなる）
- サイドバーの件数は「そのボタンだけをクエリにしたときに出る行の数」で、サブタスクだけが当たる行も数える
- 修飾キーは Slint の `KeyboardModifiers` をそのまま使う。Apple 系で Command と Ctrl を入れ替えて渡すため、
  `flequit-platform` での OS 判定は不要だった
- クエリの保存は設定の保存経路を使うが、設定画面の再描画は行わない（`SearchMemory`）。
  1 キーごとに期限ボタンのモデルを作り直さないため
- 手で選んだ追加先は「選んだ時点の既定値」と組にして持ち、クエリが変わって既定値が変わったら破棄する
- 追加直後のタスクは、クエリに合わなくても次にクエリを変えるまで一覧に残す（見えなくなるのを避ける）
- 入力候補は `PopupWindow` をやめ、検索ボックスの直下にインライン表示する（2026-09-19 実機確認で修正）。
  ポップアップが開くとフォーカスを奪い、`@` の直後に入力欄からフォーカスが外れていたため

### 2.3 実装時の判断

- 読み取りは SQLite だけなので、Automerge が遅れても画面には影響しない。Automerge を読むのは
  ゴミ箱からの復元だけで、そこには読み取りバリアを置いた
- キューの INSERT をトランザクションの最初の文にする。SQLite の読み取り→書き込みの昇格が
  ワーカーの更新と重なると、待たずに `SQLITE_BUSY` になるため
- 「反映成功」は Automerge ドキュメントへの適用成功とした。Automerge-Repo 0.3 は
  ファイル保存の完了を通知しない（失敗もログのみ）ため、それ以上は確認できない
- 入力が原因のエラー（ペイロードを読めない等）は再試行せずすぐ `failed` にする。
  再試行待ちで同じドキュメントを 10 分以上止めないため
- `SubtaskRecurrenceRepositoryTrait` の `save` / `delete_by_*` は Automerge 側が未対応
  （以前は Automerge 側のエラーで操作全体が失敗していた）。SQLite だけに書き、キューには入れない
- （2026-09-22）反映が 1 件約 45 秒かかり、終了時にフリーズしていた。原因は開発ビルドで
  Automerge が最適化なし・debug assertions ありだったことと、集合をリストで丸ごと書き直していたこと。
  開発ビルドでも `automerge` / `hexane` を最適化し、集合を「ID → エンティティ」の Map にして
  差分だけを書く形に改めた（`docs/ja/develop/design/data/automerge-structure.md`）。
  旧リスト形式は読み取り時にそのまま受け付け、最初の書き込みで Map に変換する。
  終了時は Tokio ランタイムの停止を 1 秒で打ち切る
- （2026-09-26）`failed` の再投入は「同じドキュメントで後の行が `processed` でない」行だけに限った。
  保存は行の内容でエンティティを上書きするため、古い行を後から当てると Automerge を巻き戻す。
  判定の手がかりを失わないよう、掃除はドキュメントごとに最も新しい `processed` の行を残す
- 再投入の入口は設定画面の「データ同期」（ユーザー判断で診断画面を選択）。core に `SyncDiagnosticsPort` と
  `sync_diagnostics_facades` を追加し、ViewModel は Facade だけを呼ぶ
- Automerge-Repo の停止は、同期キューのワーカーが時間内に止まったときだけ行う。
  停止後にドキュメントへ書き込むと Automerge-Repo 0.3 が panic するため。
  `DocumentManager` は `Mutex` 越しに共有されるので、停止用のハンドル（`RepoStopHandle`）を起動時に取り出しておく
- バックグラウンド移行時の反映はライフサイクル通知のスレッドで最大 2 秒待つ。OS は通知から
  すぐ戻ることを求める（Android の ANR・iOS の強制終了は約 5 秒）一方、待つ間はプロセスが止められないため
- スナップショット系の port は `AutomergeProjectRepositoryPort` ごと削除した（削除済みデータの読み書きも
  含め、core からは一度も使われていなかった）。`flequit-infrastructure-automerge` は `flequit-core` に
  依存しなくなった。スナップショットの具象メソッドは Automerge クレートのテストが使うため残した


## 3. タスク構造の変更（リストなしのタスク・任意階層のサブタスク）

- 目的:
  1. プロジェクト直下に、タスクリストに属さないタスクを置けるようにする
     （プロジェクトへの所属は必須のまま。Automerge のドキュメントがプロジェクト単位のため）
  2. サブタスクを任意の階層で持てるようにする（タスク > サブタスク > サブタスク …）
- 決定事項（2026-10-01 ユーザー確認）
  - サブタスクは独立したエンティティをやめ、**親を持つタスク**として `Task` に統合する
  - リストに属さないタスクは、サイドバーのプロジェクト（`@プロジェクト`）で表示する。
    サイドバーに「リストなし」の項目は足さない。追加先ピッカーでプロジェクト自体を選べるようにする
  - タスク一覧では全階層を入れ子で開閉できるようにする。詳細ペインはパンくずで親へ戻る

### 3.1 設計

- データモデル
  - `SubTask` / `SubTaskTree` / `SubTaskId` と `subtask_tags` / `subtask_assignments` /
    `subtask_recurrence` 系を廃止する
  - `Task` に `parent_task_id: Option<TaskId>` を足し、`list_id` を `Option<TaskListId>` にする
  - リストへの所属は最上位のタスク（親なし）だけが持つ。子は保存時に `list_id = None` に揃え、
    位置は最上位の祖先から決まる。親と子は同じプロジェクトに属する
  - 深さは無制限。親の付け替えで循環を作らせない。読み込み時に親が見つからない・循環している
    タスクは最上位として扱う（データは書き換えない）
  - 子もタスクと同じ項目（タグ・担当者・リマインダー・期間指定）を持つ。
    繰り返しは現行どおり最上位のタスクだけが持ち、次の回を作るときは子孫を構造ごと複製する
  - `TaskTree.sub_tasks` を `Vec<TaskTree>`（再帰）にし、`ProjectTree.tasks`（リストなしの最上位タスク）を足す
- SQLite（マイグレーション `m20261001_000004_task_hierarchy`）
  - `tasks` を作り直す: `list_id` を NULL 可に、`parent_task_id` を追加、
    FK は `project_id → projects`、`(project_id, list_id) → task_lists`、`(project_id, parent_task_id) → tasks`（すべて CASCADE）
  - `subtasks` を `tasks` へ移す（`parent_task_id = task_id`、旧 `completed` は状態「完了」、優先度 NULL は 0）。
    `subtask_tags` → `task_tags`、`subtask_assignments` → `task_assignments`。`subtask_recurrence` は UI から
    書いていないため捨てる。最後に `subtask*` テーブルを消す
  - 1 つのトランザクションで行う。`tasks` を参照するテーブルを先に退避・削除してから `tasks` を作り直す
    （FK が有効なままの `DROP TABLE` は暗黙の DELETE で CASCADE を起こすため）
  - タスクの削除は子孫ごと消す（再帰 CTE で子孫を集める）
- Automerge
  - `tasks` のエントリは `parent_task_id`（無ければ親なし）を持ち、`list_id` は null 可
  - 旧 `subtasks` / `subtask_tags` / `subtask_assignments` / `subtask_recurrences` は、同期キューのワーカーが
    起動時（キューを反映する前）に `tasks` / `task_tags` / `task_assignments` へ移して旧キーを消す（冪等）
  - キューに残った旧形式の行（`sub_task` 系）は読み取り、対応するタスクの操作として適用する
  - タスクの論理削除は子孫も同じ時刻で削除済みにする。復元は同じ時刻に削除された子孫も戻す
- core
  - サブタスク系の service / facade / port を消す
  - タスクの作成・更新で親を検証する（同じプロジェクト・存在する・循環しない）。
    リストの付け替えは最上位のタスクだけ。プロジェクト直下へ移す操作を足す
  - プロジェクトのタスクを 1 回で読み、木を組み立てる処理を 1 か所にまとめる
- UI
  - `SubTaskItem` / `SubTaskRow` / `SubTaskDetailView` / サブタスク専用のコールバックを廃止する
  - タスク一覧のモデルを「表示する全階層の行」の平坦な列にする（`TaskItem` に深さ・親・子の数を持たせる。
    Slint の struct は再帰できない）。開閉は行ごと。インデントは一定の深さで頭打ち。
    ドラッグでの並び替え・リスト移動は最上位の行だけ
  - 詳細ペインはどの階層でも `TaskDetailView`。親があれば先頭にパンくず（祖先、押すとそこへ移る）。
    <サブタスク> には直下の子を並べ、押すとその子へ移る。繰り返しは最上位のときだけ表示する
  - 検索: タスクを 1 件ずつ評価する。子は祖先の所属・タグ・テキストを継承し、期限・状態・担当者は継承しない。
    自分は当たらず子孫だけが当たる行は薄く表示して開く
  - 追加先: プロジェクト自体（リストなし）を選べる。保存する追加先の履歴は、リストは従来どおり ID、
    プロジェクトは `project:{id}`
  - サイドバーのプロジェクトへドロップすると、リストから外してプロジェクト直下へ移す
  - 完了済みを隠すときは、完了したタスクを子孫ごと隠す

### 3.3 実装時の判断

- SQLite のマイグレーションはトランザクション無し・プールの接続で実行されるため、
  `manager.get_connection().begin()` で 1 つの接続に固定し、`PRAGMA defer_foreign_keys` で
  途中の外部キー検査をコミット時へ回した。`RENAME` は使わず「一時テーブルへ退避 → 参照する側から削除 →
  作り直し → 戻す」とした。戻す行は親が存在するものだけに絞る（違反が 1 件でもあると起動できなくなるため）
- Automerge の旧集合（`subtasks` ほか）は起動時に全ドキュメントを読んで移すのではなく、
  そのドキュメントへ書き込む直前（同期キューの適用）とゴミ箱からの復元の前に移す。
  移す先にすでにあるキーは上書きしないので、途中で止まってもやり直せる。
  一度も書き込まれないプロジェクトの旧集合は残るが、読み取りは SQLite なので見え方は変わらない
  （将来 Automerge から SQLite を作り直す処理を作るときは、先にこの移行を通すこと）
- キューに残った旧形式の行（`sub_task` 系）は読み取り専用の種類として残し、移行後のタスクへの操作として当てる。
  `sub_task_recurrence` は何もしない
- タスクの論理削除は子孫を同じ時刻で削除済みにし、復元は同じ時刻に削除された子孫だけを戻す
  （先に個別に消した子孫は戻さない）。SQLite へ戻すときは親を先に並べ、親が無いものは最上位に戻す
- 親が見つからない・循環しているタスクは、木の組み立てで最上位（プロジェクト直下）として扱う。
  循環は輪の中で ID が最小のタスクで断つ（どの順で調べても同じ結果になる）
- 同期キューの `AutomergeChange::Task` は `Box` に入れた（`SubTask` が無くなり、clippy の
  `large_enum_variant` に当たったため）。serde は `Box` を透過するので、キューの JSON は変わらない
- 一覧の行は「表示する全階層の行」の平坦な列にした。開閉で行が増減するので、開閉のたびに一覧のモデルを作り直す
  （値の編集は従来どおり行の差分更新）
- 選択中のタスクに行が無いとき（閉じた行の下・検索で外れた）は、木から `TaskItem` を作って詳細ペインに出す。
  編集の楽観的更新は行が無ければ `selected-task` を書き換え、どちらでも親の <サブタスク> の要約を追従させる
- 並び替えは最上位の行だけ。ドロップ位置がサブタスクの行なら、その最上位のタスクの位置とみなす。
  キーボード（increment / decrement）は行の番号ではなく最上位の行を 1 つずつ動かす `move-task-by` を足した
- 繰り返しの次の回では、サブタスクのリマインダーもずれ幅だけ動かす（期限の無いタスクなら引き継がない）
- 追加先のキーは、リストはリストの ID のまま、プロジェクトは `project:{id}`。以前保存した追加先の履歴（リスト ID）はそのまま読める
- 空状態の「タスクリストを作成」はやめた。リストが無くてもプロジェクトにタスクを追加できるため
- `slint-tr-extractor` は sandbox から導入できなかったため、`.pot` / `.po` は今回増減した項目だけを手で反映した。
  既存の `.pot` は以前から参照行が古く、ソースに無い項目（`Sidebar/Tags` など）も残っている。
  次に抽出ツールで作り直すときにまとめて整う

## 4. タスク追加欄の改善（追加先のパンくず・期限の指定）

- 依頼（2026-10-02）: 追加先の選択をパンくず形式（プロジェクトとタスクリストまで。サブタスクの親は選ばない）にし、
  追加時に日時を指定できるようにする
- 設計（正本）: `docs/ja/develop/design/ui/page/main/main.md` の「クイック追加と追加先」、
  `search.md` の「7.1 タスクの追加先ピッカー」

### 4.1 手順

- [x] 追加欄を 2 段にし、上の段に追加先のパンくず（`● プロジェクト ▾ › リスト ▾`）と期限のボタンを置く
- [x] パンくずはプロジェクト・リストをそれぞれ選び直せる（`choose-add-target-project` / `choose-add-target`）
- [x] 期限は ViewModel が下書きとして持ち（`SharedState.quick_add_due`）、追加したタスクの `plan_end_date` に入れて取り消す
- [x] 翻訳・設計書・テスト（`tests/interaction.rs`、`default_in_project`）
- [x] ふだんは 1 段にし、タスクを追加しようとしている間だけ追加先と期限の段を出す（2026-10-03 依頼）
- [ ] 実機での確認（ポップアップの位置、狭い幅での表示、段の開閉、en / ja）

### 4.2 実装時の判断

- 以前の追加先ピッカーにあった絞り込み欄と「最近使った追加先」の表示はやめた。プロジェクト → リストの
  2 段で選ぶため一覧が短い。最近使った追加先は既定の追加先の決定にだけ使う
- プロジェクトを選び直したときの場所は、クエリがそのプロジェクトを指すときと同じ規則
  （最後に使った場所 → 先頭のリスト → リストなし）にした（`default_in_project`）
- 指定できるのは期限（日時）だけにした。期間・繰り返し・リマインダーはタスク詳細で設定する。
  期限を選んでいないときのカレンダーの初期値は今の日時
- 期限は追加した 1 件に付けて取り消す。入力欄の名前と同じく、追加に失敗しても戻さない
- 2 段目（追加先と期限）は、入力欄・パンくず・期限のボタン（と開いた一覧・カレンダー）にフォーカスがあるか、
  入力欄に文字があるときだけ出す。狭い幅でも同じ
- 2 段目は `if` で作り直さず常に持ち、高さ 0 と非表示で畳む。フォーカスが入力欄からパンくずへ移る途中で
  段が消える（押した要素ごと消える）のを避けるため。畳んだ間は Tab の移動先にもアクセシビリティにも出ない
- ポップアップを開くと Slint はフォーカスを取り上げ、閉じると元へ戻す。そのため開いている間は
  `PopupWindow.is-open` で「使用中」とみなす
- パンくず・期限のボタンをフォーカスできるようにした（クリックでもフォーカスが移る）。それまでは `TouchArea` だけで
  フォーカスを持てず、「周辺の部品にフォーカスがある」を表せなかった
- 2 段目を入力欄の下に置いた（前回は上）。Tab で入力欄から追加先・期限へ順に進めるため
- タスクの行を押したら一覧がフォーカスを持つようにした。行の `TouchArea` はフォーカスを動かさないので、
  そのままでは入力欄にフォーカスが残り、2 段目が閉じないため
